# UPI Registration Backend

This is the application's active Express API for manual UPI payment submission, admin verification, serial-number assignment, committee participant search, user provisioning, and check-in. It uses the application's Firebase Authentication and Cloud Firestore project.

## Requirements and setup

- Node.js 18 or newer
- A Firebase service account with access to the project's Firestore database
- A configured organization UPI ID and fee
- Firebase Storage bucket configuration only if participants may upload payment screenshots

From the repository root:

```powershell
Copy-Item .\upi-backend\.env.example .\upi-backend\.env
Set-Location .\upi-backend
npm install
npm start
```

Set these values in `upi-backend/.env` before starting:

| Variable | Purpose |
|----------|---------|
| `PORT` | API port; defaults to `5001` |
| `CORS_ORIGIN` | Comma-separated allowed frontend origins |
| `FIREBASE_SERVICE_ACCOUNT` | Full service-account JSON encoded as one environment value; alternatively, put `serviceAccountKey.json` in this folder |
| `REGISTRATION_FEE` | Registration fee in INR per participant; group payments are calculated server-side |
| `UPI_ID` | Organization's UPI ID |
| `UPI_PAYEE_NAME` | Name shown in UPI payment apps |
| `UPI_QR_CODE_URL` | Optional URL for the organization's static QR image; a payment-specific QR is generated by the frontend regardless |
| `FIREBASE_STORAGE_BUCKET` | Optional Firebase Storage bucket, required for screenshot upload |
| `CHECKIN_TOKEN_SECRET` | Long, random secret used to sign check-in QR tokens |
| `BREVO_API_KEY` | Brevo API key; keep it only in the backend environment |
| `EMAIL_FROM` | Email address of a verified Brevo sender |
| `EMAIL_FROM_NAME` | Display name for the sender |
| `EMAIL_REPLY_TO` | Optional reply-to email address |
| `ADMIN_NOTIFICATION_EMAIL` | Admin inbox for new payment verification requests; defaults to `ekadhmayogaassociation@gmail.com` |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` | In-memory API rate-limit window and request limit |

Never commit `.env` or service-account credentials. Use the real UPI ID, fee, bucket, and a securely generated check-in secret before deployment. `REGISTRATION_FEE=500` in the example file is illustrative only.

Email notifications are sent through the Brevo transactional email HTTPS API, avoiding direct SMTP connections. Create a Brevo API key and configure `BREVO_API_KEY`, `EMAIL_FROM`, and `EMAIL_FROM_NAME` in the backend environment. `EMAIL_FROM` must exactly match a verified sender in Brevo. `EMAIL_REPLY_TO` is optional. Configure `ADMIN_NOTIFICATION_EMAIL` as the destination for new payment submissions. After an admin approves payment, the backend emails assigned serial number(s) to the submitted contact addresses. Admins can retry pending notifications from the UPI payment dashboard.

Set the frontend API URL in the project-root `.env`:

```env
REACT_APP_UPI_API_BASE_URL=http://localhost:5001
```

Restart the React development server after changing environment variables.

## Payment verification model

The service does not connect to a bank or UPI provider and does not automatically verify UTRs. Submitted UTRs, amounts, dates, and screenshots are claims only. An administrator must compare the UTR and exact amount against the organization's trusted bank transaction history before approving. The API requires an explicit admin confirmation and rejects mismatched amounts.

Screenshots are optional and are only reference material. If storage is not configured, participants can still submit payment details without a screenshot.

## Firestore data

- `participants`: existing participant records, with server-managed `paymentStatus`, `registrationStatus`, serial number, check-in data, and `paymentGroupId`.
- `scores`: staff-managed scorecards with the five Asana scores, total, and automatically assigned prize place.
- `upiPayments`: a payment record per individual or school/group payment.
- `paymentReferenceClaims`: transactionally reserves unique random six-digit payment references for payment groups.
- `upiUtrClaims`: hash-keyed UTR claims for atomic duplicate prevention.
- `paymentAuditLogs`: append-only status, submission, and internal-note history.
- `serialCounters`: per-year counters updated transactionally during approval.
- `checkInAuditLogs`: successful check-in events recorded atomically with attendance.

Firestore has no relational schema migration for these collections; the backend creates documents when needed. Deploy the changed Firestore rules/index and Storage rules (which deny client access to screenshots) from the repository root:

```powershell
firebase deploy --only firestore:rules,firestore:indexes,storage
```

The API uses the Admin SDK for registration and payment writes. Firestore client rules deny direct participant creation and prevent clients/admin UI code from setting protected payment, serial, or attendance fields.

## API

### Public endpoints

| Method and path | Description |
|-----------------|-------------|
| `GET /health` | Service health check |
| `GET /api/payment/config` | Public UPI ID, payee, configured fee, and optional static QR URL |
| `POST /api/registrations` | Create an individual participant and pending payment |
| `POST /api/registrations/batch` | Create a school/group payment and its participant records |
| `GET /api/registrations/:paymentId` | Read payment status using the registration access token |
| `POST /api/registrations/:paymentId/payment-submissions` | Submit UTR, exact amount, payment time, optional UPI app and screenshot |
| `GET /api/leaderboard` | Return scored, payment-verified participants |

Registration creation returns a randomly generated, unique six-digit `paymentReference`, `paymentGroupId`, participant registration IDs, expected amount, and a one-time registration access token. The reference remains stable for that payment, is stored with the payment and participant drafts, displayed to the instructor, and prefilled in the UPI transaction reference/note. It is a payment identifier, not an authentication code; the private access token protects registration access. UPI apps may omit notes from bank records, so the code is an aid for matching only; administrators must still verify the UTR and amount against bank records. The frontend keeps the access token in the browser session and sends it as `Authorization: Bearer <token>` for participant status and payment submissions.

### Staff endpoint

Committee and admin Firebase users can search participant name, email, instructor phone, serial number, and institution:

| Method and path | Description |
|-----------------|-------------|
| `GET /api/participants/search?q=` | Search up to 20 matching participants |

### Admin endpoints

All admin endpoints require a Firebase ID token belonging to a user whose Firestore `users/{uid}.role` is `admin`.

| Method and path | Description |
|-----------------|-------------|
| `POST /api/admin/users` | Create a Firebase Auth user and Firestore user profile |
| `GET /api/admin/payments?status=ALL&q=` | Search/filter payment records |
| `GET /api/admin/payments/:paymentId/audit` | Read the payment audit history |
| `GET /api/admin/payments/:paymentId/screenshot` | Privately retrieve an optional screenshot |
| `POST /api/admin/payments/:paymentId/retry-submission-notification` | Retry an unsent admin notification for a submitted payment |
| `PATCH /api/admin/payments/:paymentId` | Mark under review, approve, reject, or record refund status/internal notes |
| `POST /api/admin/check-in` | Validate a signed QR token or check in by serial number |

Admin requests use `Authorization: Bearer <Firebase ID token>`. Approval requires `status: "VERIFIED"` and `bankRecordConfirmed: true`. Rejection requires a reason. Approval, payment status, participant confirmation, serial assignment, counter increment, and UTR claim verification are committed in a Firestore transaction. Repeating approval is idempotent and preserves the existing serial numbers.

### Check-in

The participant confirmation page shows a signed QR token for each verified registration and can be printed or saved as PDF. The admin check-in page scans the QR using the camera (HTTPS or localhost required), accepts input from a QR scanner, and provides serial-number lookup as fallback. Check-in requires a verified/confirmed payment and is atomic; a second scan reports “Already checked in.”

## Notes and deployment considerations

- The in-memory rate limiter is suitable for a single API process. Use a shared rate-limit store before running multiple instances.
- Configure Firestore and Storage IAM/rules for production and serve the frontend/API over HTTPS.
- No bank API or statement import is configured; manual bank-record verification is the only approval path.

For Render, create a Blueprint from the repository's `render.yaml`, or create a Web Service with `upi-backend/` as the root directory, `npm install` as the build command, and `npm start` as the start command. Set all required values from `.env.example` in Render's environment settings. Set `CORS_ORIGIN` to the exact Vercel frontend origin, and configure the Vercel `REACT_APP_UPI_API_BASE_URL` to the Render service URL.

Run backend unit tests with:

```powershell
npm test
```
